===============================================================================
 1. WHAT THE SCRIPT PRODUCES
===============================================================================

It draws an ERD/ERS plot: how the strength of your 8-30 Hz brain rhythm
changes after you start imagining a hand movement, measured separately at the
C3 and C4 electrodes, for left-hand and right-hand imagery.

ERD means event-related desynchronisation - the rhythm gets weaker, which
indicates that patch of cortex became active. ERS is the opposite. The plot
shows percent change from a rest baseline, so 0% means "same as rest",
-30% means the rhythm dropped by 30%, +20% means it rose.

What you are looking for: the brain is cross-wired, so imagining the LEFT
hand should weaken the rhythm at C4 (right side of the head), and imagining
the RIGHT hand should weaken it at C3 (left side).

The method follows Liu et al. 2024, Scientific Data 11:131, "Technical
Validation -> ERD/ERS", so the figures are directly comparable to that
paper's Figure 4.


===============================================================================
 2. WHERE THE DATA COMES FROM
===============================================================================

The script never asks which file is which hand. The FOLDER NAME is the label:

    D:\trainsvm\left\*.csv      every iteration in here = LEFT hand
    D:\trainsvm\right\*.csv     every iteration in here = RIGHT hand

That is the only record of what you were imagining. Nothing inside the file
says which hand.

Each CSV must have these 10 columns:

    timestamp, ch1, ch2, ch3, ch4, ch5, ch6, ch7, ch8, mark

timestamp is in microseconds and steps by 4000, which is 250 samples per
second. ch5..ch8 are unused placeholders (constant 1.1754944e-38) and are
ignored. The script reads columns 2 to 5 (ch1..ch4) and the last column.

Values are in volts in the file and are multiplied by 1e6 to give microvolts.


===============================================================================
 3. HOW MANY TRIALS, AND WHICH ONES WERE DROPPED
===============================================================================

You have 5 left-hand files and 10 right-hand files. Each is supposed to hold
five repetitions, marked 1 to 5.

    LEFT      5 files  x 5 marks = 25 possible ->  22 used
    RIGHT    10 files  x 5 marks = 50 possible ->  50 used
                                        TOTAL     72 trials

The three dropped left-hand trials:

    Left1_5.csv    mark 3   MISSING       never recorded, not in the file
    Left6_10.csv   mark 3   NO_BASELINE   starts immediately after mark 2
    left16_20.csv  mark 2   NO_BASELINE   starts immediately after mark 1

NO_BASELINE means there was less than 1.5 s of rest before the onset, so the
"baseline" second would have been the tail of the previous imagery trial
rather than rest. Comparing imagery against imagery cancels the effect, so
those trials cannot be used.

The counts are unequal (22 vs 50) purely because you recorded twice as many
right-hand sessions. This does not distort the figure, because each panel is
averaged on its own - but the left panel is noisier, because averaging 22
things cancels less noise than averaging 50. Measured on your own data,
dropping from 50 trials to 22 inflates the curve's swing by about 41%. So
part of why the left panel looks more dramatic is simply the trial count.

Iteration lengths in your recordings vary enormously:

    LEFT     9.7 s to 37.8 s    (median 18.8 s)
    RIGHT    4.9 s to 148.1 s   (median 18.9 s)

The 148.1 s one is right46_50.csv mark 4, where the mark was left switched
on. It does no harm, because only the first 4 seconds of any trial are used.


===============================================================================
 4. THE CHANNELS
===============================================================================

Your device is the LEHeadphones2. Its SDK (eeg_headphones\brain_bit\
headphones.py) writes the channel order as:

    ch1 = A1    left earlobe    reference
    ch2 = C3    left motor cortex
    ch3 = C4    right motor cortex
    ch4 = A2    right earlobe   reference

So CFG.c3 = 2 and CFG.c4 = 3, which are positions within the ch1..ch4 block
after the timestamp column has been stripped off.

Only C3 and C4 are plotted. A1 and A2 are loaded but not used.

NOTE: the other SDK in your folder (brain_bit\headband.py, the BrainBit
headband) uses T3, T4, O1, O2 instead - temporal and occipital positions with
no motor coverage. If any session was recorded on that device instead, its
trials are meaningless here and should be removed.


===============================================================================
 5. THE MARK COLUMN
===============================================================================

    mark = 0        rest
    mark = 1..5     the five repetitions in that file
    mark = 6        eyes-open baseline block, about 30 s      IGNORED
    mark = 7        eyes-closed baseline block, about 30 s    IGNORED

The mark VALUE is only the repetition number. mark 3 means "third repetition
in this file" and appears in both the left and the right folders. It says
nothing about which hand.

Marks 6 and 7 correspond to the 1-minute eyes-open and eyes-closed blocks the
paper records at the start of every session. They are skipped here, but they
are useful as a control: any analysis that can "classify left vs right" using
only those blocks is detecting the recording session, not the hand.

Note that CFG.marks = 1:5 is what defines an iteration. If you change your
recording software to use different mark values, change this setting.


===============================================================================
 6. EVERY WINDOW SIZE, WITH NUMBERS
===============================================================================

At 250 samples per second, one sample is 4 milliseconds.

  WHAT                        SECONDS     SAMPLES   SETTING
  --------------------------------------------------------------------
  Cut from the recording      6.0 s       1500      preSec+postSec+2*padSec
    padding before            0.5 s        125      padSec
    baseline                  1.0 s        250      preSec
    imagery window            4.0 s       1000      postSec
    padding after             0.5 s        125      padSec
  --------------------------------------------------------------------
  Kept after cropping         5.0 s       1250      D.nPlot
  Plotted (x-axis 0 to 4)     4.0 s       1000      postSec
  Smoothing window            0.4 s        101      smoothSec
  Rest required before onset  1.5 s        375      minRestSec

Two of these need explaining.

THE SMOOTHING WINDOW is 0.4 seconds. The paper says "smoothness coefficient
= 200", and their recordings are 500 Hz, so 200 samples is 0.4 seconds. At
your 250 Hz the same 0.4 seconds is 100 samples. The script forces it to the
nearest ODD number, 101, because MATLAB's smooth() silently reduces an even
span by 1 while movmean() does not - with an even span the two functions
disagree by about 6%, with an odd span they agree to 1e-13.

This is the general rule for moving between sampling rates: only settings
counted in SAMPLES change. The 8-30 Hz band does not change, the filter order
does not change, the 4-second window does not change. The script stores
everything in seconds and derives the sample counts from CFG.fs, so changing
CFG.fs to 500 converts all of them correctly on its own.

THE PADDING is cut and then thrown away. Filters need a run-up before their
output settles, and a 0.4 s moving average has nothing to average at the very
edge of the data, so both produce artefacts at the ends. The script filters
and smooths the 1500-sample slice, THEN trims 125 samples off each end,
leaving 1250. That pushes the artefacts outside the part you look at. The
paper does not hit this problem because their trials are 8 seconds long and
they only plot the first 5, so their edges are far off-screen.


===============================================================================
 7. HOW A TRIAL IS CHOPPED OUT
===============================================================================

Everything is measured from one moment: the ONSET, which is the first sample
carrying that mark value - the instant you clicked to start the repetition.

For each mark value 1 to 5 in each file:

  1. onset = the FIRST sample where mark equals this value.
     Using the first one matters: Right1_5.csv has mark 4 twice, and taking
     the first occurrence keeps the one with a real rest period before it and
     ignores the stray second click.

  2. Walk backwards from the onset counting contiguous mark = 0 samples.
     If that is less than 1.5 s, drop the trial (NO_BASELINE).

  3. If the onset is too close to the start or end of the file to cut the
     full 1500 samples, drop the trial (EDGE). This did not happen with your
     current data.

  4. Otherwise cut samples  [onset - 375]  to  [onset + 1124],
     which is 1500 samples by 4 channels, and stack it onto EP.

A worked example from your data. In right11_15.csv, mark 1 starts at sample
32800, which is 131.2 seconds into the recording, and the mark stays on for
17.6 seconds.

    cut       samples 32425 to 33924      1500 samples
    filter and smooth that whole slice
    crop      samples 32550 to 33799      1250 samples
    baseline  samples 32550 to 32799      the 1 s before the click
    plotted   samples 32800 to 33799      0 to 4 s after the click

Only the first 4 seconds of that 17.6-second repetition are used. The rest is
discarded on purpose: ERD is a response to an event and is strongest in the
first couple of seconds, while the later part of a long trial is mostly
attention drifting. It also means the 148-second runaway trial is harmless.

Every trial comes out the same size - 1250 samples - regardless of how long
the original repetition was. That is what makes them addable.

The result is the one data structure that matters:

    EP    [1500 samples  x  4 channels  x  N trials]

    left  EP is 1500 x 4 x 22
    right EP is 1500 x 4 x 50

Every function in the script either builds EP (loadClass) or consumes it
(erdCurve, trialErd, plotPanel, toPaperFormat).


===============================================================================
 8. WHAT HAPPENS TO EACH TRIAL - THE FOUR PROCESSING STEPS
===============================================================================

These are the paper's four steps, in erdCurve().

STEP 1 - BANDPASS 8 to 30 Hz, 2nd-order Butterworth.
  Keeps the mu (about 8-13 Hz) and beta (about 13-30 Hz) rhythms, which are
  the ones that change during imagined movement. Throws away slow drift,
  sweat and blinks below 8 Hz, and muscle activity above 30 Hz.
  Applied with filtfilt, which runs the filter forwards and then backwards
  so it introduces no time shift. The paper's TEXT specifies zero-phase; the
  paper's CODE actually uses a causal filter(), which shifts the curve in
  time. Set CFG.zeroPhase = false to reproduce their version.

STEP 2 - SQUARE IT.
  A brain wave swings above and below zero, so averaging it directly would
  cancel to nothing. Squaring makes every sample positive, and the result
  tracks how STRONG the rhythm is rather than which way it happens to point.
  This is a crude power envelope.

STEP 3 - AVERAGE ACROSS TRIALS, THEN SMOOTH.
  All 22 left trials are averaged into one curve, all 50 right trials into
  another. A single trial is far too noisy to read; the pattern only emerges
  from stacking many. Then a 0.4 s moving average removes the fast ripple
  that squaring leaves behind. This is also why the curves cannot show
  anything faster than about half a second - that detail is smoothed away.

STEP 4 - CONVERT TO PERCENT AGAINST THE BASELINE.
  M = the mean of the curve over the baseline second (-1 to 0 s).
  Result = (value - M) / M * 100.
  Brain rhythms have no meaningful absolute size, so what matters is the
  change relative to rest immediately before.

  IMPORTANT: the paper's TEXT says the baseline is the -1 to 0 s preparation
  period. The paper's CODE (PlotEvent.m) actually uses samples 500:999,
  which on its own plotted axis is 0 to 1 s - the first second of imagery.
  Normalising imagery against imagery partly cancels the effect you are
  looking for. This script uses the -1 to 0 s version from the text, which is
  also standard ERD practice.

The cropping happens between step 3 and step 4, so the baseline mean is
computed on clean, already-trimmed data.

===============================================================================
 10. THE SIGNIFICANCE TEST
===============================================================================

The averaged curve can be misleading. Because the power of every trial is
added up BEFORE the percent conversion, a few high-amplitude trials can
dominate the shape and make a pattern appear that most trials do not have.

So trialErd() repeats the whole calculation one trial at a time, giving one
number per trial: its mean ERD% over the 0 to 4 s window. Then a paired
t-test asks whether the contralateral electrode really is lower than the
ipsilateral one across trials.

    Left hand   contralateral = C4, ipsilateral = C3
    Right hand  contralateral = C3, ipsilateral = C4

For a real contralateral ERD you need the difference to be NEGATIVE and
p < 0.05 in BOTH rows.


===============================================================================
 11. EVERY SETTING YOU CAN CHANGE
===============================================================================

All of them are in the SETTINGS block at the top. Nothing below that block
needs editing.

  CFG.dataRoot      folder containing \left and \right
  CFG.outDir        where figures and files are written
  CFG.leftFolder    subfolder name for the left-hand class
  CFG.rightFolder   subfolder name for the right-hand class

  CFG.fs            sampling rate of YOUR recordings, in Hz. Every sample
                    count is derived from this, so setting it to 500 rescales
                    the smoothing, baseline, padding and axis automatically.

  CFG.band          bandpass in Hz. [8 30] is the paper. Try [8 13] for mu
                    alone or [13 30] for beta alone - they have genuinely
                    different time courses and averaging them together may
                    be hiding structure.
  CFG.order         Butterworth order. Higher is a sharper cutoff but rings
                    more. 2 is the paper.
  CFG.zeroPhase     true = filtfilt, no time shift. false = the paper's
                    causal filter(), which delays the curve.

  CFG.smoothSec     smoothing window in seconds. Smaller keeps more detail
                    and more noise.
  CFG.smoothMethod  'moving' reproduces the paper. 'sgolay' and 'loess'
                    preserve about 70% more of the peak depth. 'rlowess' is
                    robust to outlier trials and suppresses depth by about
                    30%. All except 'moving' need the Curve Fitting Toolbox;
                    without it the script falls back to a moving average and
                    still runs.

  CFG.preSec        baseline length before the onset, in seconds
  CFG.postSec       imagery window after the onset - also sets the x-axis
  CFG.padSec        margin cut and discarded. Increase if you see artefacts
                    at the edges of the plot.
  CFG.minRestSec    rest required before an onset. Lowering it would let more
                    trials through, but their baselines would be contaminated
                    by the previous trial.

  CFG.c3, CFG.c4    which column within ch1..ch4 holds C3 and C4
  CFG.marks         which mark values count as an iteration

===============================================================================
 13. CURRENT RESULTS
===============================================================================

Per-trial mean ERD% over 0 to 4 s. Negative would mean activation.

    task          n     contra      ipsi      diff         p
    Left hand    22      37.89     35.22      2.67    0.7732
    Right hand   50      30.00     28.29      1.72    0.8390

Both differences are POSITIVE, which is the opposite of the contralateral
prediction, and both p-values are around 0.8, meaning the result is
indistinguishable from random noise.

Every value is also positive in absolute terms, which means the 8-30 Hz
rhythm got STRONGER after the click rather than weaker. That is ERS, not ERD,
across the board, and it points at a recording problem rather than a
processing one.

The same analysis was independently implemented in Python and produced
+2.67 and +1.72 as well, so this is not an artefact of the MATLAB code.


===============================================================================
 14. KNOWN PROBLEMS WITH THE DATA
===============================================================================

These limit the result, and none of them can be fixed by changing the
analysis. They need a new recording session.

(a) YOU CLICKED TO START EACH TRIAL.
    Clicking is a real hand movement, produced by the same motor cortex being
    recorded, occurring exactly at the boundary between the baseline second
    and the measurement window. This alone could explain the uniform power
    increase after t = 0.
    Fix: let software show the prompt and write the marker. Keep hands still.

(b) REACTION-TIME JITTER.
    A manual mark means t = 0 varies by a few hundred milliseconds from trial
    to trial. Averaging assumes alignment; jitter of that size smears a
    1-second effect into nothing when you stack 22 or 50 trials.
    Fix: same as (a) - software-timed cues.

(c) EVERY FILE CONTAINS ONLY ONE CLASS.
    This invalidates classifier accuracy, not the ERD plot, but it is the
    most serious problem in the dataset. Because folder = class = session, a
    model tested on a trial whose siblings are in the training set only has
    to recognise the recording session. Measured on this data:
    leave-one-iteration-out gives 75-83%, leave-one-FILE-out gives 53-66%,
    and a permutation test gives p = 0.089. The honest accuracy is not
    distinguishable from chance.
    Fix: interleave left and right randomly within a single session, as the
    paper does.

(d) TRIAL LENGTH IS UNCONTROLLED.
    4.9 s to 148 s means the task was never the same length twice.
    Fix: a fixed duration, ended by the software. The paper uses 4 s.

(e) ONLY TWO ELECTRODES OVER MOTOR CORTEX.
    C3 and C4 are the correct pair and are enough for a laterality measure,
    so this is not the bottleneck. Fix (a) to (d) first.

Minimum changes worth making for the next recording session:
    1. Interleave left and right randomly within every session.
    2. Software-timed prompt, fixed 4 s imagery, fixed rest, marker written
       by the program at cue onset.
    3. Hands completely still - no clicking to start a trial.
    4. Keep the 30 s eyes-open and eyes-closed blocks as a control.
    5. Aim for 40 or more trials per class per session.
